06 Business operations

From request to purchase order, with the budget checked at every step.

a
Purchase request
draft→sourcing→pending approval→approved|rejected

Live budget check while typing. Submitting resolves the department or project budget. Over budget is flagged, not blocked.

b
Quotations, then amount-based approval
≤ SAR 50kDept. manager
≤ SAR 250k+ Finance
> SAR 250k+ Executive

Over budget always adds Finance and Executive. Nobody approves their own request.

c
Budget commitment

The final approval writes one commitment to an append-only ledger (a database trigger blocks UPDATE and DELETE) in the same transaction.

d
Purchase order
draft→issued→cancelled

Supplier, lines and prices are copied from the selected quotation. Cancelling either releases the budget once or keeps it for a linked replacement order.

Budget impact, committed on approval

08 CRM & customer journey

Every enquiry becomes a scored, owned lead, followed up on time.

a
Pipeline with rules
new→contacted→qualified→viewing→negotiation→won|lost

Moves go forward only. Won and lost need a reason. Agents see only their own leads.

b
Transparent scoring, 0–100

Points for source, contact completeness, budget, timeline, consent, and the number of available units that fit the budget. Every point is shown with its reason. No AI involved.

c
Assignment & SLA

Round-robin per project and a 48-hour follow-up. crm.follow_up_sla escalates overdue leads to sales managers once a day.

d
Reservations

One active reservation per unit (partial unique index plus a row lock), 72 hours by default. Converting sells the unit and wins the lead in one transaction. Expiry releases the unit.

Lead names are fictional test data. E-mail addresses and phone numbers are masked in every screenshot.
Rule-based score · stage · owner

10 Custom Python automation engine

PostgreSQL is the job queue.

Business serviceThe change and its event row are written in one transaction (outbox).
PostgreSQL 18automation_events · wf_definitions · wf_executions · step executions · logs · worker heartbeats
Workers 1…n claimUPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED) → running, attempt + 1, lease = timeout + 30 s
Each stepRe-locks its execution, checks owner + attempt, runs the action, checks again, commits. A worker that lost its lease commits nothing.
At-least-once delivery

Execution is idempotent per event, with slot keys for schedules. The same event processed twice creates one execution.

Retry policy

Transient errors retry with exponential backoff (30 s, 60 s, 120 s…, capped at 15 min, ±20 % jitter). Default 3 attempts. Permanent errors fail at once.

Deterministic

Conditions are plain Python. No approval or financial write depends on AI output.

Operable

Enable or disable workflows, edit parameters, view steps and logs, retry a failed run (audited).

7 workflows registered · 589 executions in the development database on 18 Nov 2026, all succeeded (scheduled runs add more every 15 min)

15 Security, governance & reliability

Seven layers of security, from the browser to the database row.

1Public edge

The public API returns allowlisted fields only · honeypot plus a signed form token with a minimum fill time · rate limits per IP and per contact · CORS limited to the two app origins

2Identity & sessions

Argon2id password hashing · signed session in an HttpOnly, SameSite=Lax cookie (Secure required outside development) · CSRF header required on every change · lockout after 5 failures for 15 min · sign-out revokes every session

3Authorisation

Every internal endpoint needs a signed-in user, enforced by the backend whatever the frontend shows · 38 permissions checked inside the services · sales agents see only their own leads

4Approvals & audit

Nobody approves their own request · authors and editors are excluded from approving their content · append-only audit log and approval decisions (database triggers)

5AI isolation

Read-only tools, run under the user's own permissions · AI never approves, posts or writes financial data · kill switch and daily cost cap · contact details redacted before the model

6Files, secrets & errors

Uploads typed by file signature, capped (10 MB images, 50 MB 3D models) and stored under random names · secrets only in the git-ignored .env, never sent to the frontend, redacted from logs; placeholder secrets refused outside development · unexpected errors return a generic message with a request ID

7Financial integrity

Money as Decimal NUMERIC(18,2) · append-only budget ledger · row locks · idempotency keys · partial unique indexes (one active reservation per unit, one active PO per request)

Checked by automated tests

  • Every non-public route rejects anonymous calls. The test walks the whole route table.
  • Public responses expose only allowlisted fields, even when a staff cookie is sent.
  • Self-approval is refused, and excluded approvers can't decide.
  • The ledger and audit rows can't be updated or deleted.
  • Concurrent commits, reservations and orders can't double-book.
  • A prompt-injection attempt causes no state change.
  • Uploads with the wrong signature, too large, or with external references are refused.
  • Missing CSRF header → refused. Lockout and session revocation work.
